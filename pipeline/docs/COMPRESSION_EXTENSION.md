# 데이터 규모 확대에 대비한 압축·사전 확장 설계

2026-11-25 결정: **압축 및 사전 코드화 최적화는 향후 데이터 볼륨이 커졌을 때 재검토하는 확장 항목으로 남긴다.** 지금은 실행 코드·기존 실시간 전송 규약·운영 설정을 변경하거나 기능을 활성화하지 않는다.

## 현재 확보한 확장 지점

| 구분 | 현재 상태 | 규모 확대 시 검토 |
|---|---|---|
| 실시간 전송 | 기존 `/v2/events` 단일 JSON 유지 | 묶음 전송·크기 기준 선택 압축 |
| 오프라인 누적 기록 | 참조 큐의 gzip 조각, 전용 수신·복원 경로를 구현·격리 시험. 운영 활성화와 실제 EXE 연결은 미완료 | 전송량·재접속 집중도에 맞춘 조각 크기·전송률 조절 |
| 코드 사전 | `offline/codebook-v1.json`과 수신 해석 지원. EXE 전체 로그의 자동 코드화는 미적용 | 절감 효과가 확인되는 필드에 한해 선택 적용·버전 확장 |
| Delta OPTIMIZE | 저장된 작은 파일 정리이며 전송 gzip과 별개 | 별도 성능 과제로 관리 |

전송 시각이 오래됐다는 이유만으로 전체 로그를 자동 gzip 처리하는 구조가 아니다. 향후에는 **누적 바이트·묶음 크기·네트워크 상태**를 기준으로 선택하는 정책을 검토한다. 압축 대상과 임계값·레벨은 아직 운영 기준으로 확정하지 않았다.

## 재검토 시 지킬 조건

- 게임 렌더 스레드에서 압축하지 않고, 조각당 반복 압축을 줄인다. SQLite 저장 잠금을 오래 잡는지도 함께 측정한다.
- 수신 시 gzip 해제·JSON 파싱·검증 시간을 분리 계측하고, 공유 collector가 실시간 요청을 지연시키지 않도록 실행 위치와 동시 처리 상한을 검토한다. 스레드 분리만으로 CPU 처리량이 보장되는 것은 아니다.
- 동일 데이터로 무압축 / gzip 레벨별 / 사전 코드화 / 병행 적용을 비교한다. 본문 바이트뿐 아니라 CPU·메모리·p95 지연·대기열·최종 DB 정합성도 확인한다.
- event_id·회원/세션 연결·sequence·원래 시각·상세값은 보존한다. 수신 측에서 기존 표준 형태로 복원한 뒤 기존 해시·중복 검증을 유지한다.
- 사전 버전과 기존 코드의 의미를 보존하고 재사용하지 않는다. 미지원 버전은 임의 해석하지 않으며, 송신자는 원본을 유지한다.
- 압축 전후 크기 제한·분할·재개·동일 ID 재전송 규칙을 유지한다. 접수 영수증과 최종 DB 적재 완료는 구분한다.

## 참고 측정과 한계

합성 오프라인 기록 735건·동일 7개 조각의 본문 비교 결과다. 사전 비교는 event_type·operation만 숫자로 바꾸고 원본으로 정확히 복원되는지 검사했다.

| 방식 | 바이트 | 원본 대비 감소 |
|---|---:|---:|
| 원본 JSON | 381,702 | 기준 |
| 사전 코드화만 | 363,455 | 4.78% |
| 실제 gzip 조각 | 29,912 | 92.16% |
| 사전 코드화 + gzip 비교 | 29,663 | 92.23% |

gzip 이후 사전 코드화의 추가 절감은 249바이트(약 0.83%)였다. 같은 gzip 레벨 9로 재압축한 원본 대조군도 29,912바이트였다. 이 표본에서는 반복 문자열을 gzip이 이미 효율적으로 압축했다. 다른 게임 데이터의 절감률이나 처리 성능 향상을 보장하는 결과가 아니다. HTTP/TLS·manifest·영수증·SQLite·Mongo/Delta 저장 공간은 제외했다.

측정 근거: [크기 비교 JSON](evidence/offline-2026-11-25/size-measurement.json). 구현·격리 시험의 상세 기록: [오프라인 동기화 검토서](OFFLINE_SYNC_2026-11-25.md).

현재 우선순위는 기존 파이프라인의 안정성과 정합성이다. **압축·사전 최적화는 확장 가능성을 문서로 남기고 보류하며, 실제 볼륨과 계측 근거가 생겼을 때 적용 여부를 결정한다.**
