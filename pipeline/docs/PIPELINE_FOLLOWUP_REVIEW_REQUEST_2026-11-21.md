# NODEVERSE 파이프라인 후속 검토 요청

2026-11-21 변경분(`cc86e7f`까지) 기준으로 아래 네 항목의 실제 영향과 수정 범위를 검토해 주세요. 코드에서 확인한 사항이며 실행 결과는 포함하지 않습니다. Kafka 토픽별 운영 현황판과 실시간 토픽별 집계는 내일 별도로 논의합니다.

## 1. 실패 급증 경보의 현재 창과 비교 기준 맞추기

- **관찰**. 현재 5분 창은 늦게 도착한 이벤트를 제외하지만, 직전 30분 기준 실패율은 지연 이벤트를 포함한 `gold.minigame_1m`에서 읽습니다. 예를 들어 오프라인 실패 기록이 한꺼번에 반영되면 과거 기준값이 높아져 이후 실제 급증을 놓칠 수 있습니다. 기존 체크포인트로 재시작하면 열린 창에 변경 전 누적값이 남는 경우도 검토해 주세요. [기준 창 계산](../spark/gold.py#L145) · [현재 창과 체크포인트](../spark/gold.py#L193)
- **요청**. 경보의 현재 창과 비교 창에서 같은 지연 제외 규칙과 실패율 산식을 사용해 주세요. 실시간 1분 현황은 기존처럼 지연 도착 이벤트를 포함해야 합니다. 배포 시 진행 중인 창을 어떻게 전환할지 정하고, 체크포인트 재생성이 필요하면 재처리 범위와 기존 경보 게시값 정리 방법을 먼저 제시해 주세요.
- **확인 기준**. 지연 실패가 대량 유입돼도 경보 비교 기준이 왜곡되지 않고, 정상 시각의 실패 급증은 포착됩니다. 실행 중인 기존 창이 있는 상태에서 재시작했을 때도 전환 동작을 설명할 수 있습니다.

## 2. Delta 압축으로 인한 실시간 처리 지연 줄이기

- **관찰**. Silver는 Outbox 적재 전에, Gold는 MongoDB 게시 전에 동기 `OPTIMIZE`를 실행합니다. Bronze 압축도 요약 및 진행 상태를 갱신하는 루프 안에서 실행됩니다. 동일 스레드 실행은 쓰기 충돌을 줄이는 데 도움이 되지만 압축 소요 시간이 적재·게시·갱신에 전파될 수 있습니다. [Silver 적재](../spark/silver.py#L113) · [Gold 게시](../spark/gold.py#L120) · [Bronze 주기 작업](../spark/periodic.py#L173)
- **요청**. Silver·Gold는 Outbox 적재와 MongoDB 게시를 압축보다 먼저 완료하는 방안을 검토해 주세요. Bronze는 상태 갱신 루프와 분리하는 방안을 확인해 주세요. 압축을 별도 실행한다면 동일 테이블의 `MERGE`·압축이 무제한 겹치지 않도록 직렬화, 동시 실행 상한, 실패 처리 방식을 함께 제시해 주세요. 게시 순서만 앞당기면 다음 배치가 계속 압축을 기다릴 수 있으므로 두 지연을 각각 확인해 주세요.
- **확인 기준**. 압축이 실행되는 배치에서 Outbox 적재·MongoDB 게시 지연, 다음 배치 시작 지연, 상태 스냅샷 갱신 간격을 각각 확인합니다. 압축 실패 시 적재·게시와 체크포인트 복구가 정상적으로 이어지는지도 확인합니다.

## 3. 원격 작업자 회원 캐시의 만료·크기·설정 적용 검토

- **관찰**. 기본 TTL 300초 동안 캐시된 회원의 `live` 상태나 매핑 변경은 MySQL에서 다시 읽지 않습니다. TTL은 캐시 적중 여부에만 쓰이며 만료된 키를 삭제하거나 전체 크기를 제한하는 코드가 없습니다. Compose 원격 작업자의 서비스 환경은 `.env.remote`로 전달됩니다. [회원 확인 캐시](../remote/projection.py#L46) · [환경 설정](../common/settings.py#L58) · [Compose 원격 작업자](../build_compose.py#L104)
- **요청**. 만료 키 정리와 최대 크기 제한을 추가하는 방안을 검토해 주세요. 회원 상태·매핑 변경의 허용 반영 시간을 정하고, 즉시 반영이 필요한 환경에서는 `.env.remote`에서 `REMOTE_MEMBER_CACHE_SECONDS=0`이 실제 컨테이너에 적용되는지 확인해 주세요.
- **확인 기준**. 반복 요청은 유효한 캐시를 활용합니다. TTL 만료나 캐시 비활성 시 변경된 회원 상태·매핑을 읽습니다. 다수의 고유 회원이 계속 유입돼도 캐시 크기가 상한을 넘지 않습니다.

## 4. Silver가 실제로 기록한 날짜 파티션을 압축 후보에 반영

- **관찰**. UUID 생성일별 `MERGE` 묶음에서 `event_date`의 최솟값과 최댓값만 압축 후보로 저장합니다. 한 묶음이 월·화·수 파티션에 기록하면 화요일은 해당 압축 회차에서 빠질 수 있습니다. [Silver 압축 후보](../spark/silver.py#L101)
- **요청**. 해당 배치가 쓴 날짜를 모두 압축 후보에 반영해 주세요. 가능하면 기존 그룹 집계에서 날짜 목록을 함께 얻어 추가 Spark 작업을 줄여 주세요. UUID 생성일 기준 `MERGE` 분할과 `event_id` 중복 방어는 유지해 주세요.
- **확인 기준**. 같은 UUID 생성일 묶음에 서로 다른 `event_date`가 세 개 이상 들어오면 중간 날짜도 압축 후보에 들어갑니다. 같은 배치를 재실행해도 Silver 중복 방어가 유지됩니다.

검토 결과에는 항목별로 확인한 영향, 수정 여부와 근거, 변경 파일 및 검증 결과를 남겨 주세요. 운영 서비스를 대상으로 한 장애 재현이나 부하 발생이 필요한 항목은 별도 시험 환경에서 확인해 주세요.
