# 적재 병목과 관측 경고 개선 — 2026-11-23

## 관측된 원인

- 실제 운영 `nodeverse-v2-live-remote-writer`는 한 건씩 처리하는 구버전이며 공용 코드의 배치·세션별 병렬 처리, 연결 풀, 대기 기한 기능이 적용되지 않았다. 테스트 1만 건 중 회원 매핑 대기와 이전 이벤트 순서 대기가 쌓여 재시도 처리량이 떨어졌다. 오래된 19건의 기한도 현재 실행 버전에서는 자동 적용되지 않는다.
- 기존 `oldest_due_age_s`는 처리 중 항목까지 최초 큐 시각으로 정렬했다. 조건 대기 후 방금 집은 이벤트도 몇 시간 처리 가능 상태였던 것처럼 표시할 수 있다.
- 수정 후 실제 DB 대조에서는 `waiting_context` 재시도 기한이 지난 이벤트가 약 1,300초 지연되어 있었다. 따라서 거짓 경고 가능성뿐 아니라 실제 적재 대기도 존재한다.
- 16시대 점검 중 Windows 호스트에서 DB 서버 .167의 TCP 3306/27017 연결은 성공했으나 서로 다른 Docker 네트워크의 컨테이너에서 .167 두 포트와 .29:8000, .81:8000에 연결이 시간 초과됐다. 실제 Mongo ping과 MySQL 연결도 적재 컨테이너에서 실패했다. Docker 네트워크는 내부 전용이 아니고 기본 경로는 있으므로 이 사실만으로 방화벽·NAT 중 특정 원인을 단정할 수 없다. 운영 연결이 불안정할 때 적재기 교체는 하지 않았다.

## 수정

- `pending`, `retrying`, `waiting_context` 중 `next_attempt_at <= 현재 시각`을 만족하는 항목만 처리 가능 지연으로 계산한다. `waiting_context`도 작업자의 실제 claim 대상이다. 각 상태별로 기존 `(state,next_attempt_at)` 인덱스에 제한된 조회를 사용한다. 실행 시각 이후부터 기존 이력 값과 기준이 다르다.
- 5분 넘게 갱신되지 않은 `processing`은 별도 경고로 표시한다. DB 오류 시 미확인을 0으로 속이지 않는다.
- 배치 후보 조회와 claim 사이에 재시도 시각이 미래로 변경되면 해당 항목을 선점하지 않도록 최종 업데이트에서도 기한을 다시 확인한다.
- Spark 의존 테스트 도구가 기본 pytest 수집을 방해하던 파일명을 수정했다.

## 운영 복구 추가 기록

2026-11-23: 내부망 연결 장애는 이 작업에서 만든 종료된 격리 시험 네트워크 `nv-writer-check2_isolated`가 실제 LAN `192.168.0.0/24`를 포함하는 `192.168.0.0/20`을 사용한 주소 충돌로 확인됐다. Docker 엔진 라우팅 테이블과 네트워크 ID를 대조했고, 연결된 컨테이너가 없는 해당 시험 네트워크만 제거한 뒤 운영 적재 컨테이너의 MySQL·MongoDB 연결이 각각 0.04초에 복구됐다. 장애를 만든 시험 네트워크를 사전에 정리하지 못한 것이 원인이다. Docker 재시작만으로는 해결되지 않았다.

이후 `nodeverse-writer-candidate:a3484f0`를 운영 remote-writer에 적용했다. `REMOTE_WORKERS=2`, `REMOTE_BATCH=30`, `REMOTE_DONE_TTL_DAYS=0`이며 완료 이벤트 자동 삭제 인덱스가 없음을 확인했다. 기존 운영 이미지는 롤백용으로 보존하고, 게이트웨이·Kafka·Spark·MongoDB는 교체하지 않았다. 시험 데이터는 삭제하지 않았다. 대기열 완료 건수가 4,680에서 5,381 이상으로 증가했고, 이후 모든 상태가 종료될 때까지 확인이 필요하다.

재발 방지: 격리 실험은 사용 중인 LAN·WSL·Docker 네트워크 대역을 사전에 확인해 겹치지 않는 명시적 서브넷을 사용하고, 종료한 실험 네트워크는 연결된 컨테이너가 없음을 검증한 뒤 정리한다. 수집·DB 네트워크에 접근하지 않는 실험은 `network_mode: none`을 우선 사용한다.

시험 Compose는 기본 사설 시험 대역 `10.203.201.0/24`와 `10.203.202.0/24`를 각각 사용한다. 실행 전 대상 PC의 LAN·VPN·WSL·Docker 대역과 겹치지 않는지 확인하고, 필요하면 `WRITER_TEST_SUBNET` 또는 `SILVER_RECOVERY_SUBNET`으로 변경한다. 내부 전용 네트워크도 호스트와 주소가 겹치면 운영 컨테이너의 경로를 가로챌 수 있다.

## 1만 건 시험 완료와 정리 전 확인

운영 적재기 교체 이후 `loadtest-20261123141721` 10,000건이 모두 stored로 전환되었다. 원격 MongoDB에서 동일 시험 ID의 원본 10,000건, 시험 회원 세션 1,429건, 문제 실행 1,429건, 풀이 시도 1,429건, 행동 기록 10,000건을 확인했다. 별도 `test-player-e2e` 원본 10건도 확인했다. 이 숫자는 전송 실패 0건이나 실제 게임 전체 부하에 대한 보증이 아니다.

정리 범위는 DB 운영자와 확인하고 백업 후 처리해야 한다. 시험 데이터가 참조한 문제 정의 1개는 다른 세션에서도 참조하므로 삭제 대상에 포함하면 안 된다. 실제 사용자 데이터와 공용 정의는 삭제하지 않았다. 기존 19건의 실사용자 순서 대기도 시험 기록과 별도이며 재처리 기한 동작을 확인 중이다.

`test-player-e2e` 전용 기록 10건은 수동으로 재시도 보관해 원본을 유지했다. 두 시험 ID의 대기열·원격 원본 각 10,010건, 시험 회원 1명, 세션·문제 실행·풀이 시도 각 1,429건, 행동 기록 10,000건과 관련 로컬 처리 상태를 별도 백업하고 파일별 SHA-256을 검증했다. 시험 세션에 다른 player_id의 이벤트가 없고 시험 회원 세션의 행동 이벤트가 대상 outbox에 포함됨을 확인했다. 공유 문제 정의 1건은 삭제 대상에서 제외한다. 공용 DB 삭제는 이 문서 작성 시 수행하지 않았다.

## 후속 보관·코드 현행화

수동 보관된 회원 매핑 대기 기록이 다른 회원의 등록이나 매핑 파일 변경 때문에 자동 재개될 수 있는 문제를 수정했다. 수동 보관은 `manual_parked`로 식별하고 자동 재개에서 제외하며, 명시적인 재처리는 가능하다. 수동 보관된 순서 대기도 선행 이벤트 도착만으로 자동 해제하지 않는다. 과거에 수동 보관했던 기록에는 이 표식이 없으므로 새 코드 배포 후 필요한 시험 기록을 다시 명시적으로 보관해야 한다.

같은 세션의 순서 누락 기록 하나가 보관되면 나머지 기록을 무조건 60초 더 늦추던 방식을 보완했다. 순서 누락으로 보관된 경우 다음 기록은 각각 원본 보존과 대기 기한을 직접 확인한다. DB 장애 등의 다른 보관 사유에서는 기존 지연 동작을 유지한다.

회귀 검사 126개 통과, PySpark 1개 건너뜀. 격리 MySQL·MongoDB에서 100개 세션 500개 이벤트 전체 저장·중복 방지 통과(4 작업자, 5.51초, 격리 1회). 시험 데이터 및 백업은 서버 담당 확인 전까지 보존한다.
