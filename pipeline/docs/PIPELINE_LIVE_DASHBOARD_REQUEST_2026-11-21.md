# NODEVERSE 파이프라인 진행 현황판 구현 요청

관리자 실시간 현황에 **`파이프라인` 탭**을 추가해 주세요. 운영자가 수집부터 최종 반영까지 어느 구간이 진행 중이고 어디에서 밀리는지 한 화면에서 볼 수 있어야 합니다. 단계 카드를 클릭하면 상세 지표와 해당 단계의 최근 로그를 표시해 주세요. [NODEVERSE 데이터 흐름 그림](../../docs/architecture/pipeline-architecture-2026-11-21.png) · [현재 실시간 화면](../../server/templates/telemetry/live.html)

## 화면과 동작

```text
게임 → 수집 API → Kafka
  nv.learning.v2 → Bronze → Silver 학습     → Gold 학습·경보 → 실시간 화면
  nv.update.v1   → Bronze → Silver 업데이트 → Gold 업데이트 → 실시간 화면
  nv.runtime.v1  → Bronze → 런타임 내보내기
  원격 내보내기 사용 시 위 두 Silver 출력과 런타임 내보내기 → Outbox → 작업자 → 원격 DB
  nv.dlq.v1      → 거절 현황(rt_rejects의 DLQ 항목)
  nv.bundle.v2   · 예약
```

- 기본 화면은 **밝은 배경의 토픽 흐름도**로 구성합니다. 왼쪽에는 수집 API가 라우팅한 Kafka 토픽을 세로로 놓고, 가운데 큰 원형 허브에는 세 토픽이 공유하는 Bronze를 표시합니다. 오른쪽에는 토픽별 처리 분기, Gold 집계와 원격 적재 목적지를 배치합니다. 첨부 GIF처럼 가는 색 띠를 따라 신호가 합류하고 갈라지는 방향을 읽을 수 있어야 합니다. 토픽을 클릭하면 관련 경로를 강조하고 같은 화면에서 단계별 로그를 확인합니다. DLQ는 독립 경로로, 예약 토픽은 연결선 없이 표시합니다.
- 활동이 확인된 구간만 짧게 강조합니다. 최신 배치나 게시 기록이 바뀌면 그 구간을 움직이고, 입력 대기·갱신 끊김·시각을 확인할 수 없는 구간은 상태만 표시합니다. 큐에 이벤트가 남고 적재도 진행 중이면 대기 상태와 처리 흐름을 함께 보여줍니다. 점은 활동을 나타내는 시각 효과이며 운영 화면에서 이벤트 수나 개별 이벤트의 이동을 뜻하는 라벨은 붙이지 않습니다.
- 카드에는 **단계명, 현재 상태, 대표 지표 한 가지**를 표시합니다. 클릭하면 하단에 마지막 갱신 시각, 처리량·지연 등 단계에 맞는 상세 지표와 **최근 로그**가 나옵니다. 화면이 갱신돼도 선택과 키보드 포커스를 유지합니다.
- 좁은 화면에서는 흐름을 세로로 재배치하고, 탭이 보이지 않으면 폴링과 효과를 멈추거나 늦춥니다. 모션 감소 설정에서는 색·텍스트로 활동을 알 수 있게 합니다.

## 단계별 지표와 출처

### 토픽별 집계

- 기본 수치는 학습·업데이트·런타임 각각의 **최근 완료된 1분 창에 해당하는 Bronze 원본 행 수**입니다. 집계 시간 기준(`kafka_ts`), 창 종료 시각과 반영 시각을 표시하고 늦게 커밋된 행은 해당 창에 반영해 주세요. 재전송된 원본 행도 포함합니다. 중복 제거 후 학습 시도 수, 오답률 등은 Silver·Gold 지표로 구분합니다. [Bronze 입력 스키마](../spark/bronze.py) · [토픽별 카운트 검증 코드](../spark/verify.py)
- 현재 진행 파일은 쿼리 단위입니다. 공용 Bronze의 `numInputRows`로 각 토픽의 행 수를 나눌 수 없습니다. 정확한 건수가 필요하면 Bronze 신규 커밋만 증분 집계하고 재시작·재처리 시 동일 커밋이 두 번 더해지지 않게 합니다. 운영 화면은 게시된 작은 스냅샷을 조회합니다. Kafka 오프셋 차이는 파티션별로 계산한 뒤 토픽별 추정값으로 표시하고, 불연속·재생성·시점 불일치 시 미확인 처리합니다.
- DLQ는 기존 `rt_rejects.dlq`의 60분·24시간 거절 집계를 사용하고 예약 토픽은 ‘예약’으로 표시합니다. 원격 내보내기가 꺼져 있으면 해당 가지에 ‘비활성’을 표시합니다. 공용 Outbox의 전체 대기량을 각 토픽의 대기량으로 복제하지 않습니다. [토픽 계약](../topics.py) · [런타임 분기](../spark/delta_stream.py)
- 현재 규모의 고정 흐름도는 Django 템플릿과 SVG로 구현할 수 있습니다. 운영팀이 별도 모니터링 화면을 사용할 경우 Grafana Node Graph의 노드·연결선 데이터셋으로 같은 스냅샷을 매핑할 수 있습니다. React 화면에서 드래그·확대가 필요해지면 React Flow의 경로 애니메이션도 검토해 주세요. [Grafana Node Graph](https://grafana.com/docs/grafana/latest/visualizations/panels-visualizations/visualizations/node-graph/) · [React Flow 경로 애니메이션](https://reactflow.dev/examples/edges/animating-edges)

| 단계 | 첫 버전 표시 항목 | 재사용할 출처 |
|---|---|---|
| 수집 API·Kafka | 수집 준비 상태, 응답 브로커 수, 비교 가능한 시점의 Kafka → Bronze 오프셋 차이 | [프로토콜 점검](../common/health.py#L135) · [적체 계산 참고](../spark/verify.py#L70) |
| Bronze·Silver·Gold | 쿼리 상태, 마지막 배치 번호·시각, 입력 행, 배치 소요 시간, 재시작 횟수 | Spark `write_progress()`가 이미 저장하는 진행 파일의 허용 필드. 입력 행은 단계별 값으로 표시합니다. [진행 파일](../spark/periodic.py) |
| Gold → 실시간 화면 | 최근 게시 시각, 게시 실패, 재게시 대기 | 기존 `rt_summary` 및 Spark의 `gold_republish_pending`. [대시보드 요약](../../server/telemetry/live.py#L62) · [Gold 재게시](../spark/gold.py#L80) |
| Outbox·원격 적재 | 대기·처리 중·완료·격리, 주요 대기 사유, 시각을 확보할 수 있으면 가장 오래된 대기 | 기존 `pipeline_sink_status`를 사용합니다. 적재율이나 최장 대기가 아직 계측되지 않았다면 출처가 확인된 지표부터 게시합니다. [Outbox 상태 게시](../remote/worker.py#L282) |
| 회원별 기록 | 마지막 완료 시각과 최근 실패·격리 결과 | 원격 작업자의 처리 완료 결과. 운영자가 특정 이벤트를 추적하는 기능은 별도 범위로 둡니다. [이벤트 적재 상태](../collector.py#L189) |

**정상 입력 대기, 적체, 갱신 끊김, 아직 관측되지 않음**을 구분해 주세요. 단계별 갱신 시각을 기준으로 판단하고, 오래된 값은 마지막으로 관측한 값으로 표시합니다. 모든 상태를 한 곳에서 중계하더라도 원격 작업자 상태와 Spark 상태의 시각은 각각 유지합니다. 오프셋을 신뢰할 수 없는 시점에는 Kafka 적체를 미확인으로 표시합니다. Gold 행 수는 집계 행 수이므로 단계 간 행 수를 빼서 유실을 판단하지 않습니다.

## 단계별 최근 로그

- 선택한 단계의 **시각·수준·메시지**를 최근순으로 보여주세요. 예를 들어 Silver는 배치 완료·실행 시간·재시작, Kafka는 적체·브로커 응답 변화, 원격 적재는 재시도·격리·회복 메시지가 표시됩니다. 갱신 끊김처럼 관측 로직이 감지한 상태와 실제 작업 로그를 식별할 수 있게 표시합니다.
- 이미 구조화된 운영 로그나 상태 변화 기록을 재사용해 주세요. 별도 저장이 필요하면 단계·시각으로 조회 가능한 작은 롤링 목록에 요약을 저장하고 최초 조회는 최근 20건 정도로 제한해 주세요. 로그 상세 조회는 선택한 카드에서만 요청합니다.
- 관리자 인증을 적용하고 운영 지표에 사용할 필드를 명시적으로 선택해 주세요. 원본 게임 페이로드, 연결 정보, 인가 헤더, 사용자 식별 정보는 요약 로그에서 제외합니다. 시안에서 사용한 예시 로그와 운영 로그는 데이터 출처 라벨로 구분합니다.

## 성능과 실패 격리

- 상태 스냅샷을 파이프라인 쪽에서 약 10초 간격으로 한 번 게시하고, 기존 Django 관리자 API 패턴으로 작은 상태 문서만 읽어 주세요. 브로커별 프로토콜 진단은 필요하면 별도의 느린 공용 수집 주기를 둡니다. 화면 요청에 Spark SQL, Bronze 전체 집계, 컨테이너 로그 수집, 전체 레코드 재집계가 따라 실행되는 구조는 피합니다.
- 상태 게시와 상세 로그 저장 실패는 주 처리 경로에서 격리해 주세요. MongoDB나 운영 상태 수집이 잠시 느려져도 Bronze·Silver·Gold 처리와 Outbox 적재가 평소처럼 이어지는지 확인합니다.
- 동작은 짧은 CSS 효과나 제한된 개수의 점으로 구현합니다. 이벤트별 DOM 생성이나 계속 도는 애니메이션은 비용과 시각적 혼동을 늘리므로 배치 또는 상태 변경 단위로 표시합니다. 단계 선택과 상태 갱신은 그림 전체를 다시 그리지 않고 필요한 부분만 바꿉니다.
- 이번 범위는 관측과 화면입니다. 원래 Kafka 토픽·수집 응답 계약, Spark 시간 창·워터마크·체크포인트, Delta Bronze·Silver `MERGE`·Gold, 원격 적재의 상태 전이는 기존 동작을 기준으로 검증합니다.

## 완료 기준

1. 대표 학습 이벤트가 들어오면 단계별 배치·게시·적재 지표가 각 출처의 갱신 주기에 맞게 바뀝니다. 카드마다 최근 로그를 확인할 수 있고 기존 학습·업데이트 탭도 동작합니다.
2. 입력 0건, Kafka 적체, 원격 적재 지연, Spark 상태 갱신 끊김을 구분합니다. 실시간 화면은 정상이고 회원별 기록만 밀리는 경우 두 분기의 차이를 한눈에 볼 수 있어야 합니다.
3. 현황판을 여러 탭에서 열어도 Kafka·Spark 진단 실행 횟수가 탭 수만큼 늘지 않습니다. 판을 닫았을 때와 열었을 때의 5분 CPU, 상태 API 응답 시간, 기존 처리 지연과 상태 조회 빈도를 비교해 주세요.
4. 모바일 너비, 키보드 조작, 모션 감소 설정에서 단계 선택과 로그 읽기가 가능해야 합니다. 운영 적용 전에 별도 시험 스택에서 정상 흐름과 실패·복구를 확인해 주세요.
