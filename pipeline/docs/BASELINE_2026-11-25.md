# 1단계 완료: 격리 환경 기준 성능 측정

2026-11-25 11:44:40~11:47:47 KST 부하 전송·적재 측정. 운영 코드 기준 e42aba5. 실제 운영 설정은 변경하지 않았다. 시험 후 시험 서비스만 정지하고 데이터 볼륨과 근거 파일을 보존했다.

## 결론

10,600개 고유 이벤트가 Bronze → Silver → 원격 원본·행동 로그까지 모두 일치했다. 누락·Silver 중복·격리·부하 단계 재시도·참조 오류는 0건이다. 하지만 고부하에서 대기열이 증가하고 수신→저장 p95가 64.3초까지 늘었다. 현재 측정에서는 Outbox 이후 적재 대기와 상류 Spark 처리 시간이 함께 증가했다. MySQL 자체가 원인이라고 특정할 SQL 쿼리별 계측은 하지 않았다.

**실제 OPTIMIZE 실행은 0회였다. 따라서 이번 지연의 원인을 압축이라고 결론 내릴 수 없다.** 압축 분리 효과는 다음 단계에서 압축이 실제 발생하는 조건으로 별도 비교해야 한다.

## 환경과 범위

- Docker/WSL 자원: CPU 16개, 메모리 약 15.44GiB. 같은 PC의 기존 운영 서비스가 함께 실행된 단일 회차 시험이다.
- 별도 프로젝트 `nv-baseline-20261125`, 별도 네트워크·Kafka·Delta·체크포인트·MySQL·MongoDB 볼륨. 호스트 노출 포트 0개. 운영 데이터 볼륨과 원격 192.168.0.167은 사용하지 않았다. 읽기 전용 데이터가 아닌 의존성 캐시 ivy만 기존 것을 공유했다.
- Kafka 3.9.1 3대, RF3 / min ISR2. 실제 모든 토픽 min ISR3, learning 6파티션 확인.
- Spark 3.5.3 / Delta 3.2.1, local[4], driver 2g, shuffle 4, Bronze 5초, 나머지 1초, Silver 중복 상태 168h. 실험적 Silver 최적화는 0, 배치 압축 주기는 300이다.
- 적재 worker 2개 스레드, batch 30, 회원 캐시 TTL 0. 대상 MySQL 8.4.13 / MongoDB 8.0.34, 로컬 큐 MongoDB 7.0.16.
- 등록된 시험 회원 50명. ST01의 정상 성공 플레이: 문제 시작 → 시도 시작 → 행동 성공 → 시도 성공 → 문제 완료, 세션당 5개 고유 UUIDv7 이벤트. 신규 게스트 생성·오류 이벤트·다양한 게임·runtime/update 경로 부하는 이번 범위에 없다.
- HTTP 송신 동시성 16. 지연은 수신기가 기록한 received_at부터 writer completed_at까지이며, 화면 표시 시간은 제외한다. 각 단계가 완전히 배출된 뒤 다음 단계로 진행했다.

## 측정 결과

워밍업 100건은 아래 비교에서 제외했다. p95는 정렬 후 ceil(0.95×N)의 최소 순위 방식이다.

| 단계 | 고유 이벤트 | 목표 접수 건/초 | 실제 접수 건/초 | 수신→저장 p50 | 수신→저장 p95 | Outbox→저장 p95 | 전송 종료 후 해소 | 관측 대기열 최대 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 낮음 | 500 | 25 | 25.0 | 11.0초 | 13.7초 | 1.9초 | 12.0초 | 121 |
| 중간 | 2,000 | 100 | 99.8 | 19.4초 | 25.1초 | 11.8초 | 22.0초 | 995 |
| 높음 | 8,000 | 400 | **242.8** | 45.3초 | 64.3초 | 47.0초 | 62.1초 | 5,598 |

고부하의 목표 400건/초는 달성하지 못했다. HTTP 응답 p50 60.4ms, p95 82.5ms와 송신 동시성 16의 제한이 함께 작용할 수 있으므로 이 결과를 ‘서버 최대 수신 성능 242.8건/초’로 해석하지 않는다. 8,000건의 전송·완전 배출 전체 95.1초 기준 완료율은 84.1건/초다. 이 값 역시 장시간 정상 상태의 최대 처리량은 아니다.

대기열은 2초 간격으로 샘플링한 Outbox의 비-stored 건수 최대치다. Kafka·Bronze·Silver에 아직 머무르는 데이터는 포함하지 않으므로 전체 미처리량이 아니다. 배출 대기는 2초 주기로 완료 여부를 확인해 약 2초의 관측 오차가 있을 수 있다.

## 병목 관찰

1. **원격 적재 대기 증가.** 부하가 커지자 Outbox→저장 p95가 1.9 → 11.8 → 47.0초로 증가했다. 고부하에서 큐가 5,598건까지 쌓였다가 완전히 해소됐다. 현재 worker 2 / batch 30 구간은 다음 튜닝 비교의 우선 대상이다. 프로세스 CPU 관측 최대 약 94%는 Docker 기준 약 1개 코어 사용량이며, SQL 자체 지연·Python CPU·왕복 요청 중 무엇이 주원인인지는 추가 계측이 필요하다.
2. **상류도 지연에 기여.** 수신→Outbox 생성 p95는 12.3 → 17.7 → 24.3초였다. 이 구간에는 Kafka 대기·Bronze 트리거·Silver 처리가 함께 포함된다. 각 구간 p95는 서로 다른 이벤트이므로 합하거나 빼서 정확한 기여율을 계산하면 안 된다.
3. **Spark 처리 비용.** 고부하 관측 표본의 Silver 배치 최대 trigger 6.23초, Gold 경보 18.59초, audit 12.11초였다. 구간 계측에서는 Silver MERGE 최대 4.96초, 계획 2.58초, Outbox 게시 1.09초가 보였다. 10초 주기 진행 파일의 마지막 배치를 2초마다 읽었으므로 모든 배치를 포착한 최대치가 아닌 ‘관측된 최대’다.
4. **자원.** 고부하 Spark 메모리 관측 최대 약 3.39GiB, CPU 약 506%였다. 전 단계 중 Spark CPU 관측 최대는 약 673%였다. Docker CPU 100%는 1개 코어 기준이며 local[4] 외 JVM·드라이버 스레드도 포함한다. OOM·컨테이너 재시작은 0건이었다. CPU·메모리는 약 6~8초 간격의 25개 표본으로, 순간 피크를 보장하지 않는다. 디스크 실제 IOPS·대역폭·SQL 쿼리별 지연은 측정하지 않았다.
5. **압축·풀스캔 근거 부족.** Delta history에서 OPTIMIZE 0회, Silver MERGE 16회를 확인했다. 작은 신규 레이크·한 날짜·한 게임 시험이므로 과거 대용량 누적 데이터의 풀스캔 병목을 재현한 것은 아니다.

운영 관측소 재확인 결과는 stored 97 / quarantined 5 / 처리·조건 대기·재시도 0, sampler 오류 없음이다. 시험 합성 데이터가 운영 DB에 들어가지는 않았다.

## 재현·근거 파일

측정 도구는 tools/baseline_stack.py, baseline_driver.py, baseline_watch.py, baseline_analyze.py, baseline_finalize.py, baseline_delta_verify.py다. 시험용 이미지가 없는 PC에서는 현재 pipeline Dockerfile과 Dockerfile.spark로 해당 태그를 먼저 빌드해야 한다. 이미지 태그는 baseline_stack.py의 설정과 맞춘다.

```text
python tools/baseline_stack.py --output <새로운 절대 출력 폴더> --project nv-baseline-<새 식별자>
docker compose -f <출력 폴더>/compose.private.json up -d kafka-1 kafka-2 kafka-3 mongo target-mongo target-mysql collector spark remote-writer
python tools/baseline_watch.py --output <출력 폴더>
docker compose -f <출력 폴더>/compose.private.json run --rm --no-deps driver python /bench/tools/baseline_finalize.py
python tools/baseline_analyze.py --output <출력 폴더>
docker compose -f <출력 폴더>/compose.private.json stop
```

Delta 검사는 시험 Spark 정지 후 시험 lake 볼륨을 `/data:ro`로 마운트한 임시 spark-submit에서 baseline_delta_verify.py를 실행한다. spark/common/tools를 각각 /app, /opt/nodeverse/common, /bench에 읽기 전용 마운트하고 결과 폴더를 /results에 마운트한다. 운영 볼륨을 대체 대상으로 지정하지 않는다.

결과 요약은 [evidence/baseline-2026-11-25](evidence/baseline-2026-11-25)에 보관한다. 전체 표본·로그·시험 Compose는 로컬 outputs/baseline-2026-11-25에 있다. compose.private.json에는 일회용 시험 자격증명이 포함되므로 Git에 올리지 않는다. 같은 프로젝트·데이터로 재실행하면 중단하도록 보호하며, 새 프로젝트와 폴더를 사용한다.

## 다음 단계 제안 — 아직 적용하지 않음

- 2단계 압축 분리: 작은 파일을 충분히 준비해 실제 OPTIMIZE를 유발하고 동일 데이터로 분리 전후를 최소 3회 비교한다. 테이블별 MERGE/OPTIMIZE 충돌·동시 작업 상한·실패 후 재시도·상태 갱신 지연을 함께 검증한다.
- 후속 적재 튜닝: worker 2→4→8, batch 30→100→200을 한 변수씩 비교하고 SQL 조회 수·응답 시간·큐 기울기를 측정한다. 회원 캐시 TTL0 정책을 임의로 바꾸지 않는다.
- 고부하 수신 한계: 송신 동시성도 따로 조절해 목표 400건/초가 실제 달성되는지 확인한다. 모든 비교는 동일 자원·반복 시험으로 진행한다.
- 운영 유사성: 별도 PC의 DB와 실제 네트워크, 다양한 게임·실패·재전송·늦은 이벤트·누적 다일자 데이터로 확장한다. 48h 중복 상태 변경은 별도 정확성 시험 후 판단한다.

이번 단계에서는 운영 성능 설정을 튜닝하거나 압축 작업을 분리하지 않았다. 기준값과 다음 비교 대상을 확보한 상태다.
