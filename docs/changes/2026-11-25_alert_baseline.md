# 실패 급증 경보 비교 기준 맞추기 (2026-11-25)

후속 검토 요청서 1번([PIPELINE_FOLLOWUP_REVIEW_REQUEST_2026-11-21.md](../../pipeline/docs/PIPELINE_FOLLOWUP_REVIEW_REQUEST_2026-11-21.md))을 반영했습니다.

## 문제

실패 급증 경보는 "지금 5분 실패율"과 "직전 30분 실패율(기준값)"을 비교합니다. 7차 보완 때 현재 5분 창은 늦게 도착한 이벤트를 빼도록 바꿨지만, 기준값은 그대로 `gold.minigame_1m`에서 읽었습니다. 이 테이블은 늦게 도착한 이벤트도 셉니다. 그래서 오프라인으로 쌓였던 실패 기록이 한꺼번에 들어오면 기준값이 높아지고, 그 뒤 실제로 실패가 급증해도 "기준값의 1.5배 이상" 조건을 넘지 못해 경보가 울리지 않을 수 있었습니다.

## 바꾼 것

| 항목 | 이전 | 이후 |
|---|---|---|
| 기준값 출처 | `gold.minigame_1m` (늦은 이벤트 포함, 1분 창) | 경보 쿼리 자신의 5분 창 `gold.failure_alerts` (늦은 이벤트 제외) |
| 기준 구간 | 시작 시각이 k-30분 ~ k 사이인 1분 창 | 시작 시각이 k-30, k-25, k-20, k-15, k-10, k-5분인 5분 창 6개. 겹치지 않고 직전 30분을 정확히 한 번씩 덮으므로 같은 이벤트를 두 번 세지 않음 |
| 늦은 이벤트 규칙 | 현재 창만 적용 | 현재 창과 기준값 모두 같은 `on_time()` 규칙 |
| 실패율 산식 | 같음 | `failures / (successes + failures)` 그대로 |
| 같은 배치에서 갱신된 창 | - | 이번 배치가 갱신하는 창은 저장된 값 대신 새 값으로 기준값을 계산 |
| Delta와 MongoDB 값 | - | 결과를 MERGE 전에 한 번만 계산(`localCheckpoint`)해서 두 곳에 같은 값을 씀 |

- 실시간 1분 현황(`gold.minigame_1m`, `rt_minigame_1m`)은 바뀌지 않았습니다. 기존처럼 늦게 도착한 이벤트를 포함합니다.
- 코드: `pipeline/spark/gold.py`의 `gold_alerts`, 새 함수 `alert_history`·`with_baseline`
- 경보 판정 조건(시도 20건 이상, 실패율 0.4 이상, 기준값의 1.5배 이상 또는 기준값 없음)은 그대로입니다.

## 배포할 때 진행 중인 창

- **체크포인트는 다시 만들지 않습니다.** 바뀐 것은 배치마다 기준값을 읽는 위치뿐이고, 스트리밍 집계(창 크기, 워터마크, 필터, 상태 구조)는 그대로라 기존 `gold-failure-alerts-v1` 체크포인트로 이어서 실행됩니다. 재처리 범위도 없습니다.
- 재시작 후 처음 갱신되는 창부터 새 기준값으로 계산합니다. 재시작 직후 30분 동안은 기준이 되는 이전 창이 재시작 전에 기록된 행입니다. 이 행들도 7차 보완(2026-11-21)부터 늦은 이벤트를 뺀 값이라 같은 규칙입니다.
- 요청서가 물은 "열린 창에 변경 전 누적값이 남는 경우"는 7차 보완 배포 때만 해당합니다. 그때 열려 있던 창은 워터마크 2분과 창 5분이 지나 이미 닫혔으므로 지금 남아 있지 않습니다.
- 이미 게시된 `rt_alerts` 문서는 정리하지 않아도 됩니다. 기준값은 창이 다시 갱신될 때만 다시 계산되므로, 닫힌 과거 창의 `baseline_rate`는 옛 방식 값으로 남습니다. 새로 갱신되는 창은 모두 새 방식 값입니다.

## 검증

- `pipeline/test_alert_baseline.py` 5개 (PySpark 필요, 없으면 건너뜀)
  - 겹치는 슬라이딩 창(k-29, k-4 등)과 현재 창을 기준값에 넣지 않음
  - 늦은 실패 대량 유입 상황: 기준값이 정상 시각 실패율(0.1)로 유지되고 실제 급증(0.75)을 경보로 잡음
  - 이전 기록이 없으면 기준값 없음, 절대 조건만 적용
  - 실패율이 계속 높으면(0.75 → 0.75) 급증으로 보지 않음
  - 같은 배치에서 갱신된 k-5 창은 새 값을 사용
- 실제 Delta(Spark 3.5.3, Delta 3.2.1)에 `gold_alerts`를 두 배치 실행: 기준값 0.1, 실패율 0.75, 경보 true가 Delta 행과 MongoDB 게시 문서에 같게 기록됨
- 파이프라인 전체 `pytest` 132개 통과 (PySpark 포함 환경)
